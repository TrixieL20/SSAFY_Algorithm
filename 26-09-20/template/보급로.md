# 접근 방법

`N × N` 지도에서 `(0, 0)`부터 `(N - 1, N - 1)`까지 이동하면서 지나가는 칸의 복구 시간 합이 최소가 되는 경로를 찾아야 한다.

상하좌우로 이동할 수 있다는 점만 보면 BFS를 떠올릴 수 있지만, 각 칸의 복구 시간이 `0 ~ 9`로 서로 다르기 때문에 단순히 먼저 방문한 경로가 최소 비용 경로라는 보장은 없다.

그래서 방문 여부를 `boolean`으로 관리하지 않고, 각 좌표까지 도달하는 데 필요한 최소 복구 시간을 `distance` 배열에 저장한다.

현재 좌표 `(y, x)`에서 다음 좌표 `(cy, cx)`로 이동할 때

```java
distance[y][x] + map[cy][cx]
```

가 기존의 `distance[cy][cx]`보다 작다면 더 좋은 경로를 발견한 것이므로 값을 갱신한다.

그리고 해당 좌표를 다시 큐에 넣어 갱신된 비용을 기준으로 주변 좌표를 다시 탐색한다.

따라서 겉으로는 BFS처럼 `Queue`를 사용하지만, 일반적인 BFS의 "한 번 방문하면 끝" 방식이 아니라 **거리 완화(relaxation)를 반복하는 방식**으로 풀이했다.

# 자료구조

* `int[][] map`
  * 각 칸을 복구하는 데 필요한 시간을 저장한다.

* `int[][] distance`
  * 시작점에서 각 좌표까지 도달하는 데 필요한 최소 복구 시간을 저장한다.
  * 처음에는 모두 `Integer.MAX_VALUE`로 초기화한다.

* `Queue<int[]> q`
  * 현재 비용을 기준으로 주변 좌표의 거리를 다시 확인해야 하는 좌표를 저장한다.

* `int[] dx`, `int[] dy`
  * 상하좌우 네 방향 이동을 처리한다.

# 핵심 아이디어

### 1. `visited`가 아니라 최소 비용을 저장

일반적인 BFS에서는 한 번 방문한 위치를 다시 방문하지 않도록 처리하는 경우가 많다.

하지만 이 문제에서는 같은 칸에 다시 도착했더라도 더 적은 복구 비용으로 도착할 수 있다.

예를 들어 어떤 좌표까지 처음 발견한 비용이 `10`이었지만 다른 경로를 통해 `7`에 도달할 수 있다면 해당 좌표의 값을 다시 갱신해야 한다.

따라서 다음처럼 방문 여부가 아니라 거리 값을 비교한다.

```java
if (distance[cy][cx] > newDistance) {
    distance[cy][cx] = newDistance;
    q.add(new int[]{cy, cx});
}
```

### 2. 거리가 갱신된 좌표는 다시 큐에 추가

어떤 좌표의 최소 비용이 변경되면 그 좌표를 거쳐 갈 수 있는 주변 칸들의 최소 비용 역시 바뀔 수 있다.

따라서 거리만 갱신하고 끝내는 것이 아니라 해당 좌표를 다시 큐에 넣는다.

```java
distance[cy][cx] = newDistance;
q.add(new int[]{cy, cx});
```

이 과정을 반복하면 더 이상 갱신되는 거리가 없을 때 각 칸의 최소 비용이 결정된다.

### 3. 다음 칸의 복구 비용을 더함

현재 위치까지의 최소 비용에 **이동할 다음 칸의 복구 비용**을 더한다.

```java
int newDistance = distance[y][x] + map[cy][cx];
```

출발점 `(0, 0)`에서는 아직 어떤 도로도 복구하지 않았으므로

```java
distance[0][0] = 0;
```

으로 시작한다.

### 4. 입력은 공백 없이 붙어 있음

지도는 다음과 같이 각 숫자가 공백 없이 한 줄로 주어진다.

```text
0100
1110
```

따라서 `StringTokenizer`로 나누는 것이 아니라 문자열의 각 문자를 숫자로 변환한다.

```java
String line = br.readLine();

for (int j = 0; j < n; j++) {
    map[i][j] = line.charAt(j) - '0';
}
```

### 5. 다익스트라와의 관계

이 문제는 각 칸의 비용이 모두 `0` 이상이고, 시작점에서 도착점까지의 최소 비용을 구하는 문제이므로 다익스트라로도 풀 수 있다.

현재 구현은 `PriorityQueue`로 가장 비용이 작은 정점을 먼저 선택하는 다익스트라가 아니라, 값이 갱신된 좌표를 일반 `Queue`에 다시 넣어 반복적으로 완화하는 방식이다.

따라서 단순 BFS라기보다는 **Queue 기반 최단거리 완화 방식**으로 이해하는 것이 더 정확하다.

# 시간복잡도

단순 BFS처럼 각 칸을 한 번만 방문하는 구조가 아니므로 `O(N²)`이라고 볼 수 없다.

한 좌표의 `distance`가 더 작은 값으로 갱신될 때마다 다시 큐에 들어갈 수 있다.

그래프 관점에서 정점은

$$
V = N^2
$$

개이고 각 정점에서 최대 4개의 간선을 가지므로

$$
E = O(N^2)
$$

이다.

Queue를 이용한 반복 완화 방식의 최악 시간복잡도는 일반적으로

$$
O(VE)
$$

까지 생각할 수 있으므로 격자에서는 이론적으로

$$
O(N^4)
$$

수준까지 증가할 수 있다.

다만 실제로는 거리 값이 감소할 때만 다시 탐색하기 때문에 불필요한 경로는 상당 부분 제거된다.

보다 일반적으로 안정적인 최단거리 복잡도를 원한다면 `PriorityQueue`를 사용하는 다익스트라로

$$
O(E \log V)
$$

에 해결할 수 있다.

# 배운 점

* 격자에서 상하좌우로 움직인다고 해서 항상 BFS를 사용하는 것은 아니다.
* BFS가 최단거리를 보장하려면 모든 이동의 비용이 동일해야 한다.
* 가중치가 서로 다른 문제에서는 `visited`보다 **현재까지의 최소 비용을 갱신할 수 있는지**가 더 중요하다.
* 이미 한 번 확인한 좌표라도 더 작은 비용으로 도달했다면 다시 탐색해야 한다.
* `distance[next] > distance[cur] + cost` 형태는 최단거리 문제에서 사용하는 핵심적인 거리 완화 조건이다.
* 이 문제의 정석적인 분류는 음수 가중치가 없는 최소 비용 문제이므로 다익스트라로 연결해서 생각할 수 있다.

# 실수한 부분

### 1. 처음에는 일반 BFS처럼 생각함

상하좌우로 이동하는 격자 문제라서 처음에는 BFS를 떠올렸다.

하지만 일반 BFS는 간선의 비용이 모두 동일할 때 이동 횟수가 가장 적은 경로를 찾는 알고리즘이다.

이 문제에서는 각 칸의 복구 시간이 다르기 때문에 이동 횟수가 적더라도 전체 복구 시간은 더 클 수 있다.

따라서 한 번 방문한 좌표를 막는 `visited`를 사용하면 안 된다.

### 2. 거리만 갱신하고 다시 큐에 넣지 않으면 안 됨

처음에는 다음과 같이 값만 변경하면 된다고 생각할 수 있다.

```java
if (distance[cy][cx] > newDistance) {
    distance[cy][cx] = newDistance;
}
```

하지만 어떤 좌표의 비용이 더 작아졌다면 그 좌표에서 이어지는 주변 경로도 새 비용을 기준으로 다시 계산해야 한다.

따라서 갱신된 좌표를 반드시 다시 큐에 넣어야 한다.

```java
if (distance[cy][cx] > newDistance) {
    distance[cy][cx] = newDistance;
    q.add(new int[]{cy, cx});
}
```

### 3. 입력 형식을 공백 기준으로 읽으려고 함

지도 한 줄은 공백으로 구분된 숫자가 아니라 하나의 문자열로 들어온다.

따라서

```java
StringTokenizer st = new StringTokenizer(br.readLine(), " ");
```

로 처리하면 두 번째 숫자부터 읽을 수 없다.

문자열을 읽고 `charAt(j) - '0'`으로 변환해야 한다.
