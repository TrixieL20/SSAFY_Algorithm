# 접근 방법

- 각 작업은 `duration(소요 시간)`과 `deadline(마감 시간)`으로 구성된다.
- 작업을 **deadline이 큰 순서대로 처리**하면서 현재 가능한 날짜를 갱신하는 방식으로 해결했다.
- 처음에는 이전에 C++로 풀었던 방식과 동일하게 `PriorityQueue`를 사용했다.
- `PriorityQueue`를 사용하면 작업을 하나씩 삽입하고 꺼내면서 deadline 순서로 처리할 수 있지만 모든 작업이 입력된 이후에는 정렬 기준이 변하지 않는다.
- 따라서 모든 작업을 배열에 저장한 뒤 deadline을 기준으로 한 번만 정렬하고 순회하는 방식으로 개선할 수 있다.

# 핵심 아이디어

- 작업을 `int[2]` 배열로 저장한다.
    - `task[0]`: 작업 소요 시간
    - `task[1]`: 작업 마감 시간
- deadline을 **내림차순으로 정렬**한다.
- 가장 큰 deadline을 시작점으로 잡고 정렬된 작업을 순서대로 처리한다.
- 현재 날짜가 해당 작업의 deadline보다 크다면 deadline까지 날짜를 당긴 후 작업 시간을 차감한다.
- 처음에는 `PriorityQueue`를 사용했지만, **입력된 작업들의 우선순위가 실행 중에 동적으로 변하지 않기 때문에** 우선순위 큐가 필요하지 않다고 판단했다.
- 배열에 모든 작업을 저장한 후 한 번 정렬하면 이후에는 단순한 순회만으로 처리할 수 있다.

# 시간복잡도

배열에 작업을 저장하는 데 `O(n)`, deadline 기준 정렬에 `O(n log n)`, 정렬된 배열을 순회하는 데 `O(n)`이 소요된다.

```
O(n log n)
```

기존 `PriorityQueue` 방식 역시 이론적으로 `O(n log n)`이지만, 모든 데이터를 미리 알고 있는 상황에서는 `PriorityQueue`의 삽입 및 삭제 연산을 반복할 필요가 없으므로 **배열 정렬 후 순회하는 방식이 더 적절하다.**

# 어려웠던 점

- 처음에는 C++로 이전에 해결했던 방식이 `PriorityQueue`를 사용하는 방식이었기 때문에 Java에서도 동일하게 구현했다.
- 알고리즘 자체는 `PriorityQueue`를 사용해 정상적으로 동작했지만 SWEA에서 **`Scanner`를 사용하면서 제한시간 초과가 발생했다.**
- Java에서 `Scanner`의 입력 성능이 제한시간에 영향을 줄 수 있다는 것을 실제 문제를 통해 체감했다.
- 이후 `BufferedReader`와 `StringTokenizer`를 사용하는 빠른 입력 방식으로 변경했다.
- 또한 `PriorityQueue`를 배열 정렬 방식으로 변경하면서, 문제의 모든 입력을 한 번에 알고 있는 경우에는 굳이 동적인 우선순위 자료구조를 사용할 필요가 없다는 점을 확인했다.

# 배운 점

- `Scanner`는 구현이 편리하지만 대량의 입력을 처리해야 하는 코딩 테스트에서는 성능 문제가 발생할 수 있다는 것을 알게 되었다.
- 단순히 기존에 사용했던 알고리즘을 그대로 적용하기보다 **현재 문제에서 우선순위가 동적으로 변하는지**를 먼저 판단해야 한다.
- 모든 데이터가 미리 주어지고 정렬 기준이 실행 중에 변하지 않는다면 `PriorityQueue`보다 **한 번 정렬한 후 순회하는 방식**이 더 단순하고 적절할 수 있다.
- `PriorityQueue`는 "항상 가장 우선순위가 높은 데이터를 꺼내야 하는 상황"에 적합하고, **처리 순서가 이미 결정되어 있다면 정렬 후 순회하는 것이 더 자연스럽다.**
